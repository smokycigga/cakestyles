# Cakestyles — Full P0 MVP Build Plan

Rebuild the cupcake_paradise codebase into the Cakestyles platform from the PRD: customer website + shareable menu + ordering on one side, and a single admin system for menu CMS, orders (all channels), CRM, enquiries, invoices, expenses, and a business dashboard on the other. Constraints from your answers: **keep the MERN stack** (MongoDB, Express, React/Vite — all running locally already), **all P0 features working**, **deployable on Vercel**.

## 1. Architecture decisions

- **Database: MongoDB (Mongoose)**, unchanged. Local dev keeps the running Docker container (`cupcake-mongo`); production uses MongoDB Atlas (free tier) — just a `MONGO_URI` env change. PRD's history-integrity rules are implemented via line-item snapshots.
- **Vercel deployment shape**: add `api/index.js` at repo root that wraps the Express app with `serverless-http` (catch-all function), plus `vercel.json` (client build output + `/api` rewrite + SPA fallback). Server dependencies move to the **root `package.json`** (required for Vercel function bundling); `server/package.json` is removed — local dev becomes `npm run dev` (server, root) + `npm run dev` (client).
- **No filesystem writes anywhere** (Vercel functions are ephemeral): image uploads are compressed client-side (canvas → ~1200px WebP) and stored in a `Media` collection; served via `GET /api/media/:id` with long cache headers.
- **Invoice PDFs generated client-side with jsPDF** — no server filesystem, no bundling issues, works identically locally and on Vercel.
- **Client API calls switch to relative `/api` paths** with a Vite dev proxy (`/api` → `localhost:5000`) — same-origin in production, no CORS config drift.
- **Email/WhatsApp**: pluggable notification module that logs for now (PRD allows "where configured"); WhatsApp stays P1.
- **Auth**: staff/admin JWT auth with **server-enforced role permissions** (owner / manager / staff / accounts per PRD §6). Open registration removed; owner account is seeded. Customers check out as guests (PRD default); order tracking via order number + phone.

## 2. Data model (server/models/)

All new models replace the existing 3; every financially meaningful record keeps snapshots (PRD §22):

- **User** — name, email, passwordHash, role ∈ {owner, manager, staff, accounts}, active.
- **Customer** — name, phone (indexed), email, importantDates[], addresses[], tags[], leadSource, marketingConsent, notes[] (author + timestamp).
- **Category** — name, slug, order, active, image.
- **Product** — name, slug, sku, category ref, short/long description, images[] (media refs), basePrice, variants[] {name, price}, addOns[] {name, price}, availability ∈ {active, paused, sold_out}, orderability ∈ {online, browse_only}, featured, tags[], prepTimeHours, taxRate, costPrice (optional), internalNotes, status ∈ {draft, published, scheduled, archived}, publishAt, seo {title, description}.
- **Media** — mimeType, data (base64), createdAt.
- **Order** — orderNumber (`CS-YYYY-####` via atomic Counter), customer ref + snapshot, **source ∈ {website, instagram, whatsapp, phone, walk_in, repeat, other} (required)**, fulfilment {type: pickup/delivery, date, slot, address}, items[] **snapshotting name/variant/unitPrice/quantity/addOns/lineTotal**, custom line items allowed (isCustom), subtotal/deliveryFee/taxTotal/grandTotal, specialInstructions, payments[] {amount, method, ref, paidAt, recordedBy}, status ∈ {pending_payment, confirmed, in_preparation, ready, out_for_delivery, completed, cancelled, refunded, partially_refunded}, statusHistory[] {status, at, by, note}, enquiry ref, createdBy.
- **Enquiry** — customer ref + snapshot, eventDate, guestCount, flavour/designNotes, budgetRange, referenceImages[], status pipeline {new → contacted → quote_sent → awaiting_confirmation → confirmed → completed/lost}, quotedAmount, notes[].
- **Invoice** — invoiceNumber (configurable prefix + sequence from Settings), customer ref, optional order ref, lines[] (catalogue or custom snapshots), subtotal/tax{rate, label, amount — configurable, no hard-coded GST}/discount/total, amountPaid, balanceDue, dueDate, status ∈ {draft, issued, partially_paid, paid, overdue, cancelled}, payments[].
- **Expense** — date, category ∈ {ingredients, packaging, rent, utilities, salaries, delivery, marketing, equipment, repairs, software, other}, description, amount, vendor, paymentMethod, attachment (media ref), recurring flag, createdBy.
- **AuditLog** — actor (user ref + name snapshot), action, entity, entityId, changes[{field, old, new}], timestamp. Written on product/invoice/expense/order-payment mutations.
- **Setting** (singleton) — store info/hours/contact/Instagram, currency INR, timezone Asia/Kolkata, tax config, pickup slots + order cutoff, delivery {enabled, fee, zones/pincodes}, allowed offline payment methods, invoice prefix/next number.
- **Counter** — atomic sequence for order/invoice numbers.

## 3. Backend (server/)

- **Middleware (finally implemented)**: `protect` (JWT verify → load user), `permit(...roles)` server-side permission matrix, audit helper, zod input validation on all writes.
- **Routes**: `/api/auth` (login, me, change-password) · `/api/media` (upload, serve) · `/api/categories` · `/api/products` (public published list w/ search/category/featured filters; admin CRUD, duplicate, bulk price/visibility/availability, CSV import/export, draft/publish/schedule/archive) · `/api/orders` (public checkout with **server-side total recomputation from DB prices**, tracking by number+phone, admin list/filter/detail, status transitions with history, manual order creation w/ custom items + deposit, payment recording) · `/api/enquiries` (public form, admin pipeline, convert-to-order) · `/api/customers` (search/filter, profile w/ computed LTV/order count/outstanding/last order, timeline aggregation, notes, tags, CSV export) · `/api/invoices` (from-order, standalone, payments, statuses) · `/api/expenses` (CRUD, category/month summary, CSV) · `/api/settings` (public subset for checkout + owner edits) · `/api/dashboard` (KPIs, sales trend, channel/product/customer breakdowns — Mongoose aggregations, all date-filtered) · `/api/reports` (CSV: sales, orders, products, customers, outstanding, expenses) · `/api/audit` (owner) · `/api/payment` (existing Razorpay create-order/verify kept).
- **Fixes to existing bugs along the way**: empty auth middleware, hash leakage in register response, mass-assignment product creation, seed-data/schema drift, no order-number, CORS via env.
- **Seed script** (`npm run seed`): owner account (env `OWNER_EMAIL`/`OWNER_PASSWORD`, dev defaults), Settings singleton, categories, demo products/customers/orders/expenses so the dashboard isn't empty.
- **Tests (vitest, server)**: cart/total recomputation, historical-price integrity (editing a product never mutates past orders/invoices), invoice total reproducibility, permission matrix enforcement, order-number sequencing. PRD §28 core invariants only.

## 4. Public website (client/src, rebranded Cakestyles)

- **Theme**: wine + pink premium identity (CSS-first Tailwind v4 `@theme` tokens), Poppins/Playfair fonts actually imported, INR formatting, mobile-first.
- **Pages/routes**: Home (hero, featured, brand points, reviews, location/hours) · `/menu` shareable digital menu (sticky category nav, search, badges Bestseller/New/Eggless/Seasonal, availability states, browse-only products) · product detail (variants, add-ons, customisation text, quantity, dietary info) · `/custom-cakes` enquiry form · About · Contact · Cart (persisted to localStorage, variant/add-on aware) · Checkout (pickup/delivery per settings, date/slot with cutoff + prep-time validation, guest details, **pay online (Razorpay) or offline method**, transparent totals) · order confirmation with order number · `/track` (number + phone) · SEO per page + product JSON-LD.
- **Menu sharing**: stable URL + QR code generation (client-side `qrcode`) with download, valid regardless of content changes.

## 5. Admin app (client/src, desktop-first, responsive)

Sidebar sections per PRD §7:

- **Dashboard** — date-filter chips (today/7d/30d/this month/last month/quarter/custom) driving all widgets: KPI cards (gross/net sales, orders, AOV, new vs repeat, outstanding, expenses, profit), recharts sales trend, channel mix, top products, expense split, recent orders.
- **Orders** — filterable table (status/source/date/search), status board view, order detail (items, payments, status timeline, customer link), **manual order creation** (customer picker with inline create, catalogue + custom line items, deposit/balance/due date) — same records as website orders.
- **Products** — full CMS form (variants, add-ons, availability, orderability, featured, tags, prep time, tax, SEO, internal notes, image upload with client-side compression), duplicate, bulk actions, CSV import/export, draft/publish/schedule, archive (never hard delete).
- **Menu** — category ordering/visibility, menu preview, share link + QR.
- **Customers** — list with search/filters, profile with full timeline (orders, enquiries, invoices, payments, notes), tags, metrics, CSV export.
- **Enquiries** — pipeline board, detail, convert-to-order flow.
- **Invoices** — list with status/outstanding filters, create from order or standalone, payment recording, jsPDF download, statuses.
- **Expenses** — list with filters, create/edit with receipt upload, category/month summaries, CSV.
- **Reports** — each report with date range + CSV download.
- **Settings** — store info, hours, pickup slots/cutoff, delivery zones/fee, tax, invoice numbering, payment methods; **Users** management (roles, deactivate); **Audit log** viewer (owner).

New client deps: `recharts`, `jspdf`, `qrcode`, `dayjs`. Root deps gain server deps + `serverless-http`; `zod`, `vitest` on server side.

## 6. Vercel deployment wiring

- `api/index.js` (serverless-http wrapper importing the Express app), `vercel.json` (client `dist` as static output, `/api` rewrite to the function, SPA fallback), consolidated root `package.json` scripts (`dev`, `seed`, `test`, `build`).
- `.env.example` + README section: MongoDB Atlas URI, `JWT_SECRET`, Razorpay test keys, owner seed credentials, local dev commands.

## 7. Implementation order

1. Server foundation: models, counters, settings, seed (owner + demo data), auth + protect/permit + audit.
2. Catalog: media upload/serve, categories, products + bulk + CSV.
3. Order engine: checkout recompute, tracking, admin orders, manual orders, payments (Razorpay + offline).
4. Enquiries → CRM → Invoices → Expenses → Dashboard/reports APIs.
5. Client API layer rewrite (relative `/api` + Vite proxy).
6. Public site rebrand + menu + detail + cart + checkout + tracking + custom cakes.
7. Admin app (all sections above).
8. Tests, Vercel wiring, docs; final end-to-end verification against PRD §25 acceptance criteria.

## 8. Out of scope (per PRD §5/§27)

Coupons/gift cards, WhatsApp automation, campaigns, recipe-level COGS, ingredient inventory, accounting integrations, Zomato/Swiggy, customer accounts/login, native app. All deferred without blocking launch.

Note: the currently running dev processes will be restarted as the structure changes (server deps move to root). MongoDB container and seeded data stay as-is; the new seed script supersedes `server/seed.js`.
